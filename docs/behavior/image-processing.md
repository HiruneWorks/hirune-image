# Image processing v1

POST /v1/images/process accepts multipart/form-data with exactly two parts: file and recipe. Either order is accepted. The recipe part has Content-Type application/json and bounded UTF-8 JSON. Unknown/duplicate parts, unknown/duplicate JSON fields, duplicate output IDs, invalid enums, invalid option combinations, and trailing multipart data fail closed. Filename and submitted file MIME never determine image format or filesystem paths.

See [recipe schema](../../contracts/image-recipe-v1.schema.json) and [example](../../contracts/examples/image-recipe-v1.json). Version is exactly 1. Outputs are an ordered array of 1–4 caller IDs matching ^[a-z][a-z0-9_]{0,31}$. Fit is inside; dimensions 1–4096; enlargement is always disabled. Lossy quality is 0–100 and effort 0–6. Lossless has effort only; quality is rejected. Effort maps to actual libwebp method. Variants run sequentially and success is all-or-nothing.

200 multipart/related contains a JSON manifest first (Content-ID <manifest>) and one WebP part per recipe output, in request array order (Content-ID <output-ID>). Every part has Content-Type and Content-Length. The manifest binds SHA-256 of exact source bytes and exact UTF-8 recipe bytes, plus output lengths/hashes and facts inspected from generated bytes. Recipe JSON is not canonicalized. Results have no EXIF/GPS/XMP/ICC/thumbnail metadata. Build/pipeline changes do not promise identical encoded bytes.

JPEG, PNG, GIF and WebP are detected from bytes and decoded. PNG supports legal depths up to 8 bits, including palette/grayscale expansion. SVG, APNG, AVIF/HEIC, HDR, 16-bit PNG and CMYK JPEG are rejected. Embedded RGB ICC (maximum 1MiB, exact declared profile length) is transformed to sRGB by moxcms before metadata removal. PNG metadata decoding has a separate 2MiB allocation budget. Unsupported/malformed profiles fail. Unprofiled ordinary images are interpreted as sRGB. Custom unprofiled PNG chromaticity/gamma and explicit HDR signaling are rejected. EXIF orientation 1–8 is applied to pixels. Resize uses linear-light, alpha-premultiplied area filtering. Lossless describes normalized/resized pixels, not reconstruction of the source file.

Animation policies are preserve, first_frame, reject. Preserve retains full composited displays, alpha, frame delays including the final frame, and total playback count. Full-canvas mux frames intentionally retain identical adjacent frames. GIF finite repeat n maps to WebP n+1; absent extension maps to 1, infinite maps to 0; overflow is rejected. WebP loop counts are retained. duration_ms is one cycle, excluding repeats. Animated zero-delay frames and animated single-frame WebP containers are rejected as unrepresentable. Positive short delays are preserved numerically; browser playback heuristics are outside this contract.

A static image has frame_count=1, duration_ms=0, loop_count=1. A one-frame GIF is treated as static. first_frame still validates and budgets the entire source; only its output becomes static. Source dimensions precede orientation; output dimensions describe actual corrected pixels.

Default simultaneous budgets: source 32MiB; complete request 33MiB; recipe 16KiB; input dimensions 8192; canvas 40M pixels; 120 frames; 100M cumulative frame pixels; 256MiB cumulative RGBA; 256MiB RGBA spool; 256MiB conservative live-pixel planning budget; 60s cycle; 32MiB aggregate output; four outputs; one admitted request; 60s absolute deadline; 10s input/output idle. The live plan reserves 20 bytes per canvas pixel, so it can reject geometry before the nominal canvas limit. All limits apply together; 256MiB cumulative RGBA becomes binding before 100M pixels. Native allocations are additionally bounded by a Linux 768MiB address-space fence and CPU limit, not by a claim that library allocations equal the pixel plan. Capabilities reports actual active settings. Windows supports functional/process tests; native memory enforcement is Linux acceptance.

Admission has no waiting queue. Overload returns 503 with Retry-After: 1 before collecting a large body. The deadline covers upload, file operations, child execution, verification and server-side delivery. An operation already submitted to filesystem I/O retains admission until its completion and cleanup, even if an HTTP timeout is returned sooner. Before success headers, timeout returns 504 JSON. After headers, failure closes the TCP connection; callers must reject incomplete multipart. Cancellation never implies instantaneous native termination; child kill/reap precedes reuse. Request directories are removed on success, failure, timeout, disconnect and shutdown.

Errors use the [fixed envelope](../../contracts/error-v1.schema.json), with code, fixed English message and request_id inside error. Status mapping: 400 invalid_request/invalid_recipe; 413 request_too_large/image_limits_exceeded/output_limits_exceeded; 415 unsupported_format; 422 invalid_image/unsupported_color_profile/animation_not_allowed/unrepresentable_animation; 503 processor_overloaded/processor_unavailable; 504 processing_timeout; 500 internal_error. No native diagnostics, filenames, source metadata or image bytes are returned in errors.

GET /health/live and /health/ready return 204 when healthy. Readiness falls during shutdown, not temporary slot saturation. Startup probes actual native codecs. GET /v1/capabilities reports effective limits and versions. GET /openapi.json serves the generated [OpenAPI](../openapi.json). [Manifest schema](../../contracts/image-manifest-v1.schema.json) describes successful JSON facts.
